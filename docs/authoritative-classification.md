# Authoritative instrument classification report

Validated 7 October 2026. Live values are time-specific.

## 1. Root issue

Unknown symbols fell back to OTHER, conflating deliberate outside-plan classification with missing knowledge. Total amounts were correct while allocation could be wrong.

## 2. Architecture

A version-controlled backend registry is the smallest robust fit for one account and a reviewed household plan. No database registry/edit UI or extra service is needed. Backend remains authoritative; frontend only displays returned buckets.

## 3. Registry structure

Immutable InstrumentClassification definitions hold symbol, explicit exchange aliases, optional reviewed instrument tokens, display name, bucket and source. NSE/BSE aliases are explicitly allowed for the reviewed instruments. Registry includes NIFTYBEES, MIDCAPETF, HDFCSML250 and ten named legacy stocks deliberately outside the plan. No tokens were guessed or seeded. Duplicate aliases/tokens (even duplicates agreeing on bucket), invalid definitions and conflicts fail at import/startup. Known token matching requires corresponding reviewed metadata to protect against reused tokens. No NIFTY/MID/SMALL/ETF name heuristics.

## 4. Classifier

apps/api/app/integrations/zerodha/buckets.py: classify_instrument(tradingsymbol, exchange, instrument_token). Holdings and trade sync call this function; holdings current allocation and snapshots use its persisted derived bucket. Activity and monthly contributions resolve execution identity through the same classifier, so registry corrections affect current reporting. Replayed actual fills update only derived bucket and existing observation/order linkage semantics, preserving immutable fill facts.

## 5. Unknown behavior

UNCLASSIFIED is a sixth bucket. Unknown data still syncs, remains visible and contributes to portfolio/purchase totals. It does not become OTHER. New ORM and database defaults are UNCLASSIFIED. Existing historical OTHER values are preserved.

## 20. Limitations

Registry updates need reviewed code changes and a refresh to materialize current holdings/stored execution classifications. Current activity/contribution read classification can change when registry definitions change; earlier snapshots do not. Tokens are supported but none are currently pinned without a reviewed identity source; explicit exchange/symbol aliases are used. Registry is household classification, not automated market-cap discovery. Newly listed/renamed instruments remain UNCLASSIFIED until reviewed. Earlier OTHER snapshot values cannot be retrospectively distinguished from unknown without evidence and were not rewritten. Monthly history remains incomplete; gross delivery buys are recorded purchases, not verified external cash contributions. Auth, cash normalization, trade identity, order semantics and read-only boundary are unchanged by this request. Nothing deployed, staged, committed or pushed.
